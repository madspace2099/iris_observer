4. THE OWNERSHIP RULE
================================================================================

THIS MIGRATION OWNS ONE JOB NAME: observer-prune-ai-rate-buckets.

  4a. A DIFFERENTLY NAMED JOB whose command mentions an Observer retention
      function stops the migration BEFORE IT WRITES ANYTHING.
  4b. A JOB HOLDING OUR NAME under another owner or database is refused rather
      than deleted.
  4c. ONLY THEN does it unschedule — filtered by jobname AND database AND
      username — and schedule one job. cron.unschedule appears exactly once in
      the file.
  4d. The postcondition is asserted in the transaction; otherwise everything
      rolls back, including the cleanup function.

WHAT THE DETECTOR CANNOT SEE. It is a substring scan over cron.command. It
catches the realistic collision and cannot catch a wrapper function, a quoted
identifier, a run-time EXECUTE, or a longhand DELETE. A guard, not a proof.

================================================================================
6. WHAT REMAINS UNPROVEN
================================================================================

  1. That pg_cron executes anything. PGlite has no postmaster and no background
     worker, so every local result about scheduling is about the CONTENT of a
     cron.job row.
  2. That cron.schedule and cron.unschedule behave as Supabase documents.
  3. That the pg_cron scheduler process stays alive on this project.
  4. Advisory-lock behaviour under real concurrency.
  5. Cost at scale. {{BUCKETS}} rows measures nothing.
  6. cron.job_run_details growth — pg_cron does not clean it up and nothing in
     this release prunes it.
