2. FOUR STATEMENTS ABOUT THE DEPLOYED BUILD, KEPT APART
================================================================================

The previous bundle said environment configuration is unknown from this session
and then concluded that the existing `3f298a6` deployment "remains pepper-less",
"keeps returning 503 permanently", and that "only the fresh deployment has the
variable". None of that follows from UNKNOWN. Corrected, and held apart:

  PROVEN        The existing deployment retains the environment snapshot
                captured when it was BUILT. Vercel applies environment-variable
                changes only to NEW deployments; a later project-level change
                does not alter an existing snapshot.

  UNKNOWN       Whether that snapshot contains `OBSERVER_SUBJECT_PEPPER`, and
                whether the value is valid. No tooling in this session exposes
                Vercel environment-variable names, scopes or values.

  UNOBSERVED    How that deployment behaves now. It may answer; it may return
                503. No HTTP request has been made to it from any of this work,
                and neither behaviour has been seen.

  REQUIRED      It is INELIGIBLE for the controlled legacy proof, because its
                configuration snapshot is UNVERIFIED. A fresh deployment of
                exact SHA `3f298a6`, built after the pepper state is settled, is
                the required controlled target — whether or not the old one
                happens to work.

The rule is about eligibility, not a predicted failure. Five regression tests in
`supabase/test/rollout-order.test.ts` hold these four apart and fail on each of
the old phrasings.

WHY IT MATTERS. `3f298a6` IS the commit that made the pepper mandatory. Its gate
returns 503 for every question when the variable is missing or malformed —
before admission, before an audit row, before any model call. A deployment of
that commit without it answers nothing at all.

The four properties "does it work?" used to collapse:

  1. database RPC signature compatibility   PROVEN
  2. application runtime readiness          NOT PROVEN (depends on the pepper)
  3. environment configuration              UNKNOWN FROM HERE
  4. observed HTTP behaviour                NEVER ATTEMPTED

7. THE THREE VERIFIERS, AND WHAT EACH ONE ASKS
================================================================================

  observer-http-compat-proof.sql   Did the deployed build write the audit row it
                                   was supposed to write? Four modes; the mode
                                   decides the expectation. 13 rows.

  observer-ai-readiness.sql        Did a MODEL answer? A different question: the
                                   compatibility proof accepts
                                   `deterministic_composer` as a complete pass,
                                   correctly, so a deployment with no
                                   `OPENAI_API_KEY` reads 13/13 while never
                                   calling a model. 11 rows.

  observer-contract-readiness.sql  May the contract migration be applied? It can
                                   never say READY. Its external gate now covers
                                   both retirement capabilities above.

ROW 11 OF THE READINESS GATE now reads ONE definition — the conjunction of all
ten conditions — instead of two of them. It has three sentences:

  live AI is answering
      exactly one row, state complete, response_source model, model_attempted,
      model_authored, no fallback_reason, provider openai, non-empty attempted
      model, non-empty author model, and the two models equal.

  Observer application works, but live AI is not yet enabled
      a VALID composer row. Report exactly this — never "the AI is working".

  Live AI is not proven — see the failed checks
      anything else, including a row labelled `model` whose other columns
      contradict it. "Not live" and "inconsistent" are different findings.
