A — A SECRET-SHAPED LITERAL WAS IN REACHABLE HISTORY, IN THIS SUITE'S OWN
    FIXTURE.

The detector fixture that proves the no-secret-recipe scanner catches an API-key
assignment contained one, written out in full. Deleting it from the working tree
made the repository WORSE rather than better: the commit that added it and the
commit that removed it both remain in history, so a scan over
`origin/main..HEAD` found the literal twice instead of once, in diffs that
cannot be edited without rewriting the commits that carry them.

Two corrections, and both were needed:

  * THE FIXTURE ASSEMBLES ITS VALUE AT RUN TIME. Fragments are joined into the
    shape the auditor refuses; no tracked byte carries the assembled string. A
    test asserts this directly, with `git grep -F` over tracked text for the
    assembled value — so the fixture cannot quietly regress into a literal.
    THIS IS NOT AN ALLOWLIST AND NOT AN OBFUSCATION: the scanner is unchanged,
    has no exception for these files, and still refuses the assembled value.
  * THE TWO LOCAL-ONLY COMMITS WERE REWRITTEN, under explicit authorisation and
    only above `7ac84fa`. Nothing at or before `7ac84fa` was touched, nothing
    pushed or deployed was touched, and nothing was force-pushed — the rewritten
    commits had never left this machine. The result is verified by identity, not
    by assertion: the new commit's TREE hash equals the old one's
    (`cba383d0e0069df63967bc898f08b477cc50b4bb`), and `git diff` from
    `7ac84fa` to each of the two heads hashes identically
    (`b872d6e1afe3618a7b441d0c6987d53b50e7a698c61f501adac6a5a1da63042c`), so
    the content is provably unchanged and only its packaging into commits
    differs. The discarded commits are unreachable: reflogs expired, `git gc
    --prune=now` run, no ref names them. The recovery patch written before the
    rewrite was itself scanned clean and then removed.

`node scripts/secret-audit.mjs` is now clean across all four of its passes —
working tree, staged diff, `origin/main..HEAD` history, and the browser bundle.

NO SECRET WAS INVOLVED AT ANY POINT. The fixture value never was a credential;
it has the SHAPE the auditor looks for, which is the entire reason the fixture
exists.

B — THE TESTS THAT VERIFY THE PACKAGER WERE GUARDED ON THE PACKAGER'S OWN
    PRECONDITION.

The packager refuses without a current, green `.release/gate-results.json`, and
that is right. But the suites that exercise it were guarded on the SAME
condition — `describe.runIf(gateRecordIsCurrent)` — and one of them additionally
on `_review/<head>` already existing.

That is circular. The record is written at the END of the gate, so during a
fresh commit's own authoritative run the guard was false and TWENTY-TWO TESTS
DID NOT RUN — seven control-character package tests and fifteen
package-generation tests — in the run whose output is the evidence that the
package is sound. The staged-package secret scan made twenty-three, guarded on
`_review/<head>` and therefore skipped everywhere the package had not already
been built, which is every machine that had not already built it.

The fix is not to relax the precondition, and there is no test-only bypass.
`packagingProblems()` is now a pure function of its three inputs, and
`build(out, { gateRecordRoot })` chooses WHERE the record is read — never
WHETHER it is checked. Each suite writes its own structurally valid synthetic
record into its own temporary root, and
`supabase/test/support/synthetic-gate-record.ts` asserts that record satisfies
the real `gateRecordProblems()` contract before returning it. A fixture that
could not pass the real contract would make every test built on it meaningless.

No test reads, writes or deletes the developer's real `.release/` directory any
more, and no test requires an earlier bundle to be on disk.

C — THE SKIPPED COUNT MEASURED THE DEVELOPER'S DISK.

The skipped total moved between two runs of the same commit — 24, then 23 — and
the record could not say which case had moved, because it stored a number and
not an identity. The cause was the guards themselves: they were conditioned on
untracked, gitignored state — whether `.release/gate-results.json` existed,
whether `_review/` held two delivered archives, whether the working tree
happened to be dirty — so the count tracked the contents of directories that are
not in the repository.

THE FOUR GUARDS AND WHAT EACH ONE COST, since a drifting total is only
explicable once the parts are named:

  7   control-character package tests   `.release/gate-results.json` is current
  15  package-generation tests          the same record, plus a clean tree
  1   staged-package secret scan        `_review/<head>` already on disk
  2   archive-inventory comparisons     two delivered ZIPs in `_review/`
  1   `spawnSync` signal reporting      the platform — the only legitimate one

Every combination of the untracked ones is reachable, which is why 24 and 23
were both observed at one commit and why neither could be explained from the
record: it stored a total and no identities. THIS IS NOT A DIAGNOSIS OF WHICH
RUN WAS WHICH — that evidence no longer exists — it is the reason no total was
diagnosable.

Every one of those guards is gone. The dirty-tree refusal is now asserted from a
literal through `packagingProblems()` rather than by waiting for somebody to
have uncommitted work; the archive-inventory checks compare each present archive
against the recorded snapshot instead of pairwise, which needs no second
archive; and the record-shape check reads the runner's source and a record it
writes itself.

ONE SKIP REMAINS, and it is inapplicable by PLATFORM rather than by state:
`spawnSync` signal reporting, which Windows does not have. Its reason is in its
TITLE — "(POSIX only; skipped on win32)" — because the record stores a suite
basename and a bounded title and nothing else. Section 7 now prints the skipped
tests BY IDENTITY, so a count is never reported without saying which case it is.

D — A FAILURE MESSAGE COULD HAVE CARRIED ANYTHING INTO THE RECORD.

`.release/gate-results.json` is staged into the archive. Vitest's JSON report
carries `failureMessages` — the assertion's `expected` and `received` rendered
as text — and this repository's own suites assert over environment names,
resolver inputs and fixture values.

The reduction from report to record was inside `run-gates.ts`, whose module
executes the whole gate on import, so the claim "no message reaches the record"
could not be tested at all. `summarizeReport()` now lives in `gate-run.ts`,
is pure, and names every field of its result explicitly rather than copying an
object through — so a field the reporter adds later reaches the record only if
somebody puts it there deliberately.

It is tested by driving a report whose failure message carries a secret-SHAPED
value, assembled at run time, through `summarizeReport()` and
`classifyTestGate()`, and asserting the auditor's own rule does not match the
serialized result. The hostile case includes a NUL, backspaces and four thousand

A — THE CONTROL-CHARACTER GATE WAS A SENTENCE, NOT A MEASUREMENT.

The gate contract accepted any verdict text for the scan unless it contained the
uppercase word FAILED. Two strings that permitted packaging:

    "raw-NUL scan": "8 FOUND"
    "raw-NUL scan": "BROKEN"

Neither contains the word, so neither was rejected. A gate whose result is a
COUNT cannot be checked by reading prose about it.

The record now carries structured evidence — `scannedFiles`, `foundCharacters`,
`affectedFiles` — and the contract checks it as data. Every field must be
present and correctly typed; the count must be exactly zero; the file list must
be empty; the two halves must agree with each other; the scan must have looked
at something; and the recorded verdict string must be the one that describes
THAT scan, so a clean-looking sentence beside a non-zero count is itself a
refusal. Absent, malformed, negative, fractional and non-zero values all refuse.

B — THE SCAN RAN IN THE WRONG PLACE, AND THE ARCHIVE PROVED IT.

The delivered `1b8b912` archive contained EIGHT literal BACKSPACE bytes — two in
patch 0034, four in 0035, two in 0036 — under the heading "control-char scan 0".
Both halves of that are explicable and neither is acceptable:

  * THE PATCHES ARE FAITHFUL. Those bytes are in the repository's history: they
    are the REMOVED lines of the three commits that removed them. A diff
    without them would be a wrong diff.
  * THE SCAN NEVER SAW THEM. It ran over tracked files, before `format-patch`
    had written a single patch. Its number was true about the working tree and
    silent about everything the packager produces.

There are three scans now, and they are reported as three:

    tracked working tree     the gate, over every tracked file
    staged package           after staging and rendering, before the manifest
    written archive          every entry inflated back out of the ZIP

The second and third refuse the build outright, and a failing archive is
DELETED rather than left on disk. None of them is summarised into the others.

C — HOW THE HISTORICAL PATCHES TRAVEL.

History is not rewritten and the patches are not excluded from the scan. Each
patch from a DECLARED commit — three of them, named by full SHA with a reason
each in `scripts/release/transport-safe.ts` — ships base64-encoded instead of
raw, with `patches/TRANSPORT-SAFE.txt` beside them.

THOSE FILES ARE NOT DIRECTLY `git am` APPLICABLE. They decode to bytes identical
to what `git format-patch` produces, so the recovered patch is applicable and
its hash is the patch's hash — but the shipped bytes are base64 and the document
says so rather than implying mail-patch applicability. Every other patch is raw
and directly applicable, and the manifest lists what is actually present.

The list is keyed on the COMMIT, not on "whatever contains a control character".
Encoding by content would turn the package scan into a formatting step: an
accidental byte in a new patch would be quietly encoded away instead of
refused. A control character in any other patch still fails the build, and the
tests inject one into a patch, a rendered evidence file, the staged gate record,
a staged generator and the manifest to prove each refuses.

A — A FOREIGN ORIGIN COULD PASS AS THE APPROVED PROJECT.

`projectRef()` parsed the URL and returned `hostname.split(".")[0]`. That is
the first label of ANY host, so both of these resolved to the approved ref and
produced `MAPPED`/PASS:

    https://<approved-ref>.example.com             — a foreign origin
    https://<approved-ref>.supabase.co.evil.test   — suffix confusion

Neither is the Observer database, and the failure is silent in the worst way:
the operator sees exactly the ref they expected and records the mapping as
proved. A rule that reads one label of a hostname is not checking the hostname.

Only the canonical hosted origin is accepted now —
`https://<project-ref>.supabase.co`, at most one trailing slash — as an
anchored whole-string pattern plus an independent URL parse that must agree with
it. That rejects by construction, not by enumeration: every foreign domain,
every extra label before or after `supabase.co`, `http`, userinfo, an explicit
port including the `:443` that WHATWG parsing silently normalises away, any
path beyond `/`, query strings, fragments and a trailing dot. The public URL is
validated identically, and an unparseable public value is its own STOP rather
than being folded into "the two disagree" — one of them names nothing at all,
which is a different fact. Twenty invalid origins are asserted to reach STOP and
never PASS, in both positions.

SCOPE, stated rather than assumed: this release targets HOSTED Supabase. A
self-hosted deployment has a different origin shape and does not get one here,
because accepting a shape this project does not use is how the hole appeared.

B — PAUSE LED NOWHERE.

8. HOW THIS PACKAGE WAS GENERATED, AND HOW TO REBUILD IT
================================================================================

TWO COMMANDS, IN THIS ORDER, and the first is not optional:

  pnpm release:gates
  pnpm release:package --verify

THE ARCHIVE IS NOT REPRODUCIBLE FROM TRACKED FILES ALONE, and this package does
not claim it is. `pnpm release:gates` writes `.release/gate-results.json`, which
is generated rather than tracked, names the commit it was recorded at, and is
staged into the archive as `gate-results.json`. A clean checkout reproduces the
same bytes only after running the gates at the same commit — which is the point:
an archive whose verification evidence could be reproduced without running the
verification would not be evidence.

The packager REFUSES if that gate record is missing, stale, recorded for
another commit, or not clean on every required gate. There is no
"GATES NOT RECORDED" archive any more, and no "STALE" one either.

It stages every input from a tracked source, so it can be run repeatedly from
nothing:

  scripts/release/live-snapshot.ts   the one recorded observation of the live
                                     database and the deployment inventory.
                                     Every artefact renders its live numbers
                                     from here; none carries its own copy.
  docs/release/*.txt                 the authored evidence, with doubled-brace
                                     placeholders for everything that changes.
  scripts/release/facts.ts           resolves those placeholders from git, the
                                     snapshot and the files themselves.
  scripts/release/wrap-migration.ts  renders the paste wrappers from the
                                     migration sources.
  scripts/release/secret-recipes.ts  the detector, shared with the test suite.
  scripts/release/zip.ts             the deterministic writer.

THE CHECKS THAT RUN BEFORE AN ARCHIVE IS WRITTEN, any of which refuses the
build:

  1. HEAD is the expected commit and the working tree is clean.
  2. No placeholder is left unresolved, and none is defined but unused.
  3. SEMANTIC CONSISTENCY. Every evidence file agrees with the snapshot and
     with git on: the current HEAD, the remote and deployed heads, the
     local-only commit set, the observation timestamp, the oldest bucket age,
     and the current candidate SHA in the compatibility table. THIS IS THE
     CHECK THE LAST PACKAGE NEEDED. Its hash-prefix validation passed on a file
     that named `c6fdc73` as the current candidate one commit after it stopped
     being one: the prose was stale and its file hash was perfectly correct.
  4. HASH ACCOUNTING. Every hexadecimal token of eight or more characters in an
     evidence file must be a prefix of a hash this package can account for — a
     packaged file, a computed historical value, or a git commit in this chain.
     Pure-decimal runs are migration timestamps and are skipped.
  5. NO RUNNABLE SECRET RECIPE in any packaged file, using the same detector
     the test suite uses.
  6. Every wrapper body equals its migration source.

WHAT THESE CHECKS CANNOT DO. They verify that a NUMBER matches its source and
that a HASH matches its bytes. They cannot verify that a SENTENCE is true.
"Comment-only", "unchanged", "byte-identical" are claims, which is why the
evidence prints the comparison rather than asserting the conclusion.

DETERMINISM. Entry names use forward slashes — every archive up to and including
the ee954b8 bundle stored Windows separators, which APPNOTE 4.4.17.1 forbids and
`unzip` warns about; the f1dbffd bundle was the first written by a conforming
writer. Entries are sorted. The timestamp is the commit date read through UTC
accessors, so the bytes do not depend on the builder's zone; this is asserted by
building under three different `TZ` settings and comparing.

  Archive          IRIS-Observer-{{HEAD_SHORT}}-review.zip
  Entries          {{ARCHIVE_ENTRIES}} files, forward-slash separators, deterministic
  Manifest         hashes.txt — {{MANIFEST_FILES}} files, `#`-prefixed prose, so
                   `sha256sum -c hashes.txt` runs without warnings

  THE ARCHIVE'S OWN SHA-256 IS NOT INSIDE THE ARCHIVE. Embedding it would change
  the bytes it describes. The packager prints it and the covering report states
  it; distribute it alongside the archive, and do not look for it within.
