1. WHAT THIS ROUND FIXED
================================================================================

FINDING 1 — the migration that performs the retirement told the operator the
wrong retirement policy.

`20260826090000_observer_audit_facade_cleanup.sql` is the file somebody opens at
the moment they are about to close the door. Its comments still said:

  * retire "every deployment carrying a build older than the
    admission/completion code" — an inventory selected by AGE, when the property
    that matters is CAPABILITY, and the two do not coincide;
  * that a protected deployment "cannot reach this database because it cannot
    reach its own route handler" — which is false for the case that matters;
  * that `vercel ls iris-observer` enumerates the deployments — with no mention
    that it is paginated;
  * that a recent `audit_version = 1` row is THE contradiction test — one axis,
    and not the one that catches the leak.

Comments only, in both the migration source and its paste wrapper. They now say
what the corrected rollout says: two capabilities, classified separately;
version-1-capable admission builds DELETED; legacy-façade-only builds deleted OR
protected, because this migration genuinely removes the function they call; that
this migration does NOT disable thirteen-argument admission; that every
`3f298a6` build including the fresh proof Preview is version-1-capable; that
`1ee5d2d` is neither; that enumeration follows `--next` to exhaustion and is
repeated after deletion; and that the database verifier reads both axes from
`retirement_floor_ts` and can return only NO-GO, UNUSABLE or INCONCLUSIVE.

FINDING 2 — the paste wrappers were maintained by hand.

Each wrapper's header asserts "Everything between BEGIN and COMMIT is
byte-identical to that file" and prints the source's sha256. Nothing enforced
either claim; the wrapper was a copy somebody kept in step. That is exactly the
failure mode this milestone exists to close, one level down.

`scripts/release/wrap-migration.ts` now renders every wrapper from its source.
The proof that it renders faithfully rather than merely plausibly is that,
BEFORE the contract source was edited, it reproduced three of the four
hand-written wrappers BYTE FOR BYTE — including migration 4's, whose hash
`a2ec32264583f5d57b87d0db089d4a707de8b317786624084a4e4a2b61b1eef5` was
independently verified in the previous review. Only the contract wrapper
differs, and only because its source changed.

FINDING 3 — four operational artefacts still carried the superseded policy.

  * `supabase/README.md` said a deployment "must be deleted or genuinely
    protected" if it can call a façade OR write `pseudonym_version = 1`. One
    remedy for two capabilities. It is now a table, with the reason the remedies
    differ attached.
  * `PEPPER-CONTRACT.txt` said the preflight determines project mapping
    "THROUGH METADATA ONLY". Names and scopes cannot prove which database a
    deployment talks to — the project is in `SUPABASE_URL`'s VALUE, which is
    compiled into the browser bundle and is not a secret. Split into part one
    (mapping, from the non-secret URL) and part two (pepper presence, type and
    scope, from metadata), with neither reading a secret value.
  * `COMPATIBILITY-EVIDENCE.txt` used `c6fdc73` as the current candidate a
    commit after it stopped being one, quoted an oldest-bucket age the snapshot
    contradicted, claimed the inventory was unchanged across "seven
    consecutive bundles" while a different paragraph implied eight, and omitted
    the current HEAD from the not-deployed set.
  * `docs/18-deployment.md` and the verifiers already agreed; a new test now
    keeps all five in step.

FINDING 4 — the no-secret-recipe guard did not do what its comment claimed.

It required a generator pattern AND a SEPARATE print pattern on the same line,
while its comment claimed it caught the OpenSSL random generator. It did not. A
generator whose default destination is standard output needs no print statement
to leak:

  [removed command that generated random material and wrote it to stdout]
  [removed command that returned a UUID, printed by the shell]
  [removed pipeline that read the kernel random device and rendered it as hex]

all pass a check that is looking for `console.log`. The detector now separates
SELF-PRINTING commands, which are an offence on their own, from PAIRED ones,
which need a generator plus an emitter — and still permits the runbook to say
that `randomUUID()` is where the non-secret request id comes from.

IT IMMEDIATELY FOUND ONE. The previous `REVIEW.txt` reproduced the removed
one-liner as executable text, inside the very section explaining that the
repository must not ship it. A description of a command is not a command; this
file now carries the bracketed descriptions above, and the packager refuses to
build an archive containing a runnable one.

Two exemptions are deliberate and narrow: `patches/` and `*.patch`, because a
patch that REMOVES a bad line necessarily contains it and rewriting history to
satisfy a linter is worse than the linter being narrow; and the detector's own
fixtures, because a test proving a recipe is caught has to contain one.

One pattern was REMOVED from the detector after it fired wrongly: Ruby's `puts`
is also an ordinary English verb, and it flagged the paragraph explaining that a
command "puts it in the shell history" — the sentence that removed the recipe. A
real Ruby one-liner is still caught, by its interpreter invocation.

FINDING 5 — the documented generator sequence could not be run twice.

`REVIEW.txt` §8 told a reviewer to run four scripts in order. The first,
`bundle.mjs`, began by deleting `_review/f1dbffd` — the directory containing the
other three, and the three hand-authored evidence files, none of which it
recreated. The second command in the documented sequence no longer existed.

Alongside that: a hard-coded `C:\Users\42191\AppData\Local\Temp\claude\...`
path; a requirement that seven earlier review ZIPs be present; a ZIP timestamp
built from `getHours()`, so the "deterministic" archive had different bytes
under UTC, Europe/Budapest and America/New_York; a `hashes.txt` whose prose
header made `sha256sum -c` emit warnings for every non-hash line; and a claim
that the archive's own hash appeared in `REVIEW.txt`, which it did not and
cannot.

There is now ONE tracked entry point, `scripts/release/build-package.ts`, which
lives outside the output directory, stages every input from tracked sources,
and builds the package from nothing. It refuses to run unless HEAD is clean, and
derives the package name, the headings and every commit-dependent fact FROM
HEAD rather than from a constant. Temporary space comes from `os.tmpdir()`. The
ZIP timestamp uses UTC accessors. `hashes.txt` prefixes every prose line with
`#`, so a standard checker consumes it silently.

THE OUTER ZIP HASH IS NOT IN THE ZIP. It cannot be: adding it would change the
bytes it describes. It is printed by the packager and reported alongside the
archive, and it must be distributed with the archive rather than looked for
inside it.

8. HOW THIS PACKAGE WAS GENERATED, AND HOW TO REBUILD IT
================================================================================

One tracked entry point, outside the output directory:

  pnpm release:package

It stages every input from a tracked source, so it can be run repeatedly from
nothing:

  scripts/release/live-snapshot.ts   the one recorded observation of the live
                                     database and the deployment inventory.
                                     Every artefact renders its live numbers
                                     from here; none carries its own copy.
  docs/release/*.txt                 the authored evidence, with doubled-brace
                                     placeholders for everything that changes.
  scripts/release/facts.ts           resolves those placeholders from git, the
                                     snapshot and the files themselves.
  scripts/release/wrap-migration.ts  renders the paste wrappers from the
                                     migration sources.
  scripts/release/secret-recipes.ts  the detector, shared with the test suite.
  scripts/release/zip.ts             the deterministic writer.

THE CHECKS THAT RUN BEFORE AN ARCHIVE IS WRITTEN, any of which refuses the
build:

  1. HEAD is the expected commit and the working tree is clean.
  2. No placeholder is left unresolved, and none is defined but unused.
  3. SEMANTIC CONSISTENCY. Every evidence file agrees with the snapshot and
     with git on: the current HEAD, the remote and deployed heads, the
     local-only commit set, the observation timestamp, the oldest bucket age,
     and the current candidate SHA in the compatibility table. THIS IS THE
     CHECK THE LAST PACKAGE NEEDED. Its hash-prefix validation passed on a file
     that named `c6fdc73` as the current candidate one commit after it stopped
     being one: the prose was stale and its file hash was perfectly correct.
  4. HASH ACCOUNTING. Every hexadecimal token of eight or more characters in an
     evidence file must be a prefix of a hash this package can account for — a
     packaged file, a computed historical value, or a git commit in this chain.
     Pure-decimal runs are migration timestamps and are skipped.
  5. NO RUNNABLE SECRET RECIPE in any packaged file, using the same detector
     the test suite uses.
  6. Every wrapper body equals its migration source.

WHAT THESE CHECKS CANNOT DO. They verify that a NUMBER matches its source and
that a HASH matches its bytes. They cannot verify that a SENTENCE is true.
"Comment-only", "unchanged", "byte-identical" are claims, which is why the
evidence prints the comparison rather than asserting the conclusion.

DETERMINISM. Entry names use forward slashes — every archive before {{HEAD_SHORT}}
stored Windows separators, which APPNOTE 4.4.17.1 forbids and `unzip` warns
about. Entries are sorted. The timestamp is the commit date read through UTC
accessors, so the bytes do not depend on the builder's zone; this is asserted by
building under three different `TZ` settings and comparing.

  Archive          IRIS-Observer-{{HEAD_SHORT}}-review.zip
  Entries          {{ARCHIVE_ENTRIES}} files, forward-slash separators, deterministic
  Manifest         hashes.txt — {{MANIFEST_FILES}} files, `#`-prefixed prose, so
                   `sha256sum -c hashes.txt` runs without warnings

  THE ARCHIVE'S OWN SHA-256 IS NOT INSIDE THE ARCHIVE. Embedding it would change
  the bytes it describes. The packager prints it and the covering report states
  it; distribute it alongside the archive, and do not look for it within.
